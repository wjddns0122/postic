## 1. 한 줄 요약

옷에 달린 BLE 태그를 매장 게이트가 자동으로 인식하고, 손님은 폰으로 "지금 앞에 걸린 옷"을 보고 피팅 요청·결제·픽업까지 끝낸다.

> 오프라인 상품이 온라인으로 연결되는 리테일의 시작 · POSTIC (Battery-free Smart Inlay · Store Node · Retail OS)

## 2. 왜 만드나

| 대상 | 지금의 문제 |
|---|---|
| 손님 | 재고·사이즈를 물어보려면 직원을 기다려야 한다. 고르기 → 피팅 → 결제가 매번 끊긴다. |
| 매장 | POS는 "팔린 것"만 남긴다. 어떤 옷이 관심을 받았는지, 피팅만 하고 안 샀는지는 기록이 없다. |

기존 대안의 한계: POS(계산대에서만 기록) · RFID 계산대(고정된 자리에서만 인식) · 카메라 비전(설치비가 비쌈).

POSTIC은 옷 자체에 붙은 태그 + 매장 게이트로 "어떤 옷이 지금 어디 있는지"를 실시간으로 알고, 그 위에 손님 앱과 매장 데이터를 올린다.

## 3. 지금까지 된 것

### 3-1. 중간평가 시연 (2026-10-27)
- 실물 비콘 3개 → 게이트 → 서버 → 웹까지 3/3 실시간 인식 확인.
- 손님 흐름(인식 → 상품 → 목 결제 → 픽업 번호)과 직원 처리 → 손님 화면 즉시 반영까지 시연.

### 3-2. 공개 시연 대비 (2026-11-13)
- Figma 디자인 시스템으로 전 화면 리디자인 (토큰·컴포넌트는 `src/index.css`, `src/ui.tsx`).
- 실제 옷 3벌로 교체, 스튜디오 컷(앞·뒤)과 행거 일러스트, 앞↔뒤 돌려보기.
- 피팅룸(`/fitting`)·1F 픽업 데스크(`/pickup`) 화면 추가, 모든 카드가 눌린다.
- 여러 사람이 동시에 쓰는 구조:
  - 기기마다 토큰이 생겨 "내 주문"만 보인다.
  - 주문은 서버 함수로만 생성되고, 기기당 10분 5건으로 제한된다.
  - 직원 화면은 PIN으로 잠긴다.
- 트래픽 테스트(무료 플랜): 가상 기기 180대 동시 접속에서 조회 실패 0건. 직원이 상태를 바꾸면 손님 화면까지 p95 0.2초 안에 도착했다.
- 실사용: 당일 여러 명이 동시에 썼다 (주문 29건, 기기 6대).
- 시연 중 읽기 전용 실시간 모니터 `node scripts/watch.mjs`.

### 3-3. ERP 백엔드 (2026-11-16)
- 직원 계정·역할(owner/manager/staff)과 작업 기록, SKU별 재고 이력(입고·판매·반품·조정), 주문 취소·환불과 매출 집계, 태그 분 단위 기록과 "자리 비움" 분석을 실DB에 추가했다.
- 기존 사이트는 그대로 동작한다. 기존 테이블·함수는 바꾸지 않고 덧붙이기만 했다.
- ERP 화면은 아직 없다 (디자인·프론트 담당). 쓸 수 있는 데이터와 함수는 [erp-api.md](erp-api.md)에 정리했다.

### 3-4. 아직 안 된 것 (일부러 뺀 것 포함)
- 배터리 없는 인레이: 지금은 배터리 비콘 FSC-BP106로 대신한다.
- 실제 결제(PG): 목 결제만 있다.
- 정밀 위치(AoA·삼각측량): 게이트 1대 + 신호 세기로 "바로 앞/근처"만 구분한다.
- 로그인·회원, POS/ERP 연동, 여러 매장.
- 상품 등록 화면: 서버 함수(`erp_save_product` 등)는 준비됐고, 화면은 아직 없다.
- 가격: 시연용 임시값(129,000 / 89,000 / 59,000)이다.

## 4. 사용자와 화면

### 손님 (모바일 웹, 375~430px)
| 경로 | 화면 | 하는 일 |
|---|---|---|
| `/` | 홈 | 인식 상태(인식됨 · N벌), 프로모션, 내 진행 중 주문, 행거 목록, 기기 토큰 |
| `/hanger/:id` | 앞에 걸린 옷 | 행거 일러스트(감지된 옷 강조), 상품 리스트(가격·사이즈·바로 앞/근처) |
| `/p/:id` | 상품 상세 | 앞↔뒤 돌려보기, 사이즈·재고, 태그 정보, 피팅하기 / 구매하기(결제 시트) |
| `/order/:id` | 주문 번호 | 픽업·피팅 번호, 상태(준비 중 → 준비 완료 → 완료) 실시간 |
| `/fitting` | 피팅룸 FR-03 | 피팅 요청 현황 |
| `/pickup` | 1F 픽업 데스크 | 픽업 대기 현황 |

### 직원 (태블릿·노트북, `/admin`, PIN 필요)
- 태그 온라인 N/N, 태그별 신호·마지막 수신
- 주문·피팅 목록과 상태 버튼
- 인식 기준(신호 세기 임계값, 온라인 유지 시간)
- 장비 장애 대비 시뮬레이터. 켜면 모든 화면에 "시뮬레이션" 배지가 뜬다.
- 게이트 원본 데이터

### 지켜야 할 규칙
- 모든 상태 변화는 새로고침 없이 반영한다.
- 가짜 데이터를 진짜처럼 보이게 하지 않는다. 시뮬레이터 데이터가 있으면 배지를 반드시 띄운다.

## 5. 시스템 구조

```
FSC-BP106 ×3 (BLE 비콘, 옷 1벌당 1개)
   │ BLE 광고 (iBeacon / Eddystone URL·TLM)
   ▼
Minew G1 게이트웨이 (Wi-Fi → 폰 핫스팟)
   │ HTTPS POST, JSON-PREPARSED, 1초마다
   ▼
Supabase Edge Function `g1-ingest`  ── 비콘 MAC → 상품 매핑 → tag_presence 갱신
   │
   ├─ 손님·직원 웹이 2초(태그) / 6초(주문·설정)마다 조회
   └─ 주문 변경은 Broadcast로 즉시: device:<기기토큰>, staff:orders
   ▼
React 웹 (Vercel)  https://postic-three.vercel.app
```

- 백업 게이트: G1이 안 되면 노트북 블루투스로 대신 수신 (`scanner/scanner.py`), HTTPS가 안 되면 노트북 중계 (`relay.mjs`).
- 인식 판정은 클라이언트에서 한다: 마지막 수신이 유지 시간(기본 10초) 안이고, 신호 이동평균이 임계값 이상이면 "인식됨".
- 무료 플랜 한도 때문에 Postgres Changes(실시간 구독)는 쓰지 않는다. 구독자가 수십 명만 돼도 타임아웃이 났다. 그래서 조회와 Broadcast를 섞었다.

### 데이터 (Supabase, 서울)
| 테이블 / 함수 | 용도 |
|---|---|
| `products` | 상품(이름·브랜드·가격·색·소재·사이즈별 재고·사진·행거·비콘 MAC) |
| `tag_presence` | 태그별 마지막 수신 시각·신호·게이트 |
| `orders` | 구매/피팅 요청, 상태, 픽업 번호, 기기 토큰 |
| `settings` | 인식 기준 (전원 공유) |
| `gateway_raw` | 게이트가 보낸 마지막 원본 |
| `place_order()` | 주문 생성 (금액은 서버가 정함, 기기당 10분 5건) |
| `staff_check()` · `staff_set_order_status()` · `staff_update_settings()` | 직원 PIN 확인 후에만 실행 |

웹에서 테이블에 직접 쓰는 권한은 막혀 있다. 쓰기는 위 함수로만 된다.

## 6. 기술 스택과 폴더

- 프론트: React 18 · Vite 6 · TypeScript · Tailwind v4 · React Router 6 · supabase-js
- 백엔드: Supabase (Postgres, Edge Function/Deno, Realtime Broadcast)
- 배포: Vercel (프론트), Supabase (DB·함수)
- 하드웨어: Feasycom FSC-BP106 ×3, Minew G1 (펌웨어 g1-e-grapes)

```
src/            웹 (pages/ 화면, components/ 행거·3D·관리자, ui.tsx 공통 컴포넌트, lib.ts 데이터·API, live.tsx 실시간)
supabase/       migrations/ DB 스키마·함수 (순서대로), functions/g1-ingest/ 게이트 수신
scripts/        loadtest.mjs 트래픽 테스트, watch.mjs 실시간 모니터, cutout/compose.swift 사진 가공
scanner/        노트북 BLE 백업 게이트 (Python)
relay.mjs       노트북 HTTP 중계 (백업)
public/products 상품 사진 (앞·뒤·컷아웃)
docs/           기획·디자인 문서
```

## 7. 다음 단계 (제안: 같이 정할 것)

아래는 정운이 정리한 제안이다. 확정이 아니니까 우선순위는 같이 정한다.

### P0. 같이 일할 준비 (이번 주)
1. **개발용 서버 분리.** 지금은 DB 하나를 시연과 개발이 같이 쓴다. 개발용 Supabase 프로젝트나 브랜치를 하나 더 만들어서, 개발 중에 실서비스 데이터를 건드리지 않게 한다.
2. **권한 공유.** GitHub는 레포 협업자로 초대한다. Supabase·Vercel은 팀 초대를 할지, 개발용만 줄지 정한다.
3. **작업 규칙 합의.** 아래 8장을 보고 합의한다.

### P1. 제품 다듬기
- 직원용 상품 관리: 상품 추가·수정, 비콘 MAC 연결, 재고 수정을 SQL 없이 화면에서.
- 실제 가격·상품 정보 반영.
- 매장 데이터 화면: 옷별로 "앞에 머문 시간·피팅 요청·구매"를 집계. POSTIC이 말하는 "POS가 못 남기는 데이터"를 직접 보여주는 핵심 기능이다.
- 보안 정리: 수신 키(`postic` 고정) 교체, 직원 PIN 교체 절차, 조회 권한 최소화.

### P2. 확장 실험
- 행거·게이트 여러 개 (행거별 위치 구분)
- 결제 연동 검토 (토스페이먼츠 등 테스트 모드)
- 사업계획 로드맵: 02 인레이 시제품(100EA) → 03 초도 생산(1,000EA) → 파일럿 매장 PoC → POS·ERP 연동

## 8. 같이 일하는 방법 (제안)

- **브랜치:** `main`은 항상 배포 가능한 상태. 작업은 `feat/…`, `fix/…` 브랜치에서 하고 PR로 합친다. 상대가 한 번 보고 머지한다.
- **배포:** Vercel 자동 배포는 연결하지 않았다. 실서비스 배포(`vercel --prod`)는 정운이 한다. 사람들이 쓰는 중에는 배포하지 않는다.
- **DB 변경:** `supabase/migrations/`에 `YYYYMMDDHHMMSS_이름.sql`로 추가하고, 먼저 개발용 DB에 적용해 본다. 실DB에는 리뷰 후에 적용한다.
- **비밀값:** `.env`는 커밋하지 않는다. 필요한 키 이름은 `.env.example`에 있고, 값은 직접 받아서 채운다. 직원 PIN, 게이트 비밀번호, 토큰은 채팅·이슈·커밋에 쓰지 않는다.
- **디자인:** UI 작업 전에 `DESIGN.md`를 읽는다. 색·간격은 `src/index.css` 토큰을 쓰고 새 값을 직접 박지 않는다.
- **할 일 관리:** GitHub Issues에 올리고, 라벨은 `hw` / `web` / `db` / `design`.
